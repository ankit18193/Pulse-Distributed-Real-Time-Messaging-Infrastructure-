## Problem Statement

High-throughput distributed real-time messaging engines like Pulse typically require an external edge reverse proxy (such as Envoy, Nginx, or Traefik) to handle perimeter concerns: edge token-bucket rate limiting, TLS termination, path routing, JWT validation, circuit breaking, and connection draining. 

However, running sidecar proxy containers or secondary in-process proxy servers introduces severe operational penalties:
1. **Sidecar / Port Proliferation**: Consumes duplicate ports, requires multi-container orchestration (Kubernetes pods or Docker Compose), and doubles socket buffer memory.
2. **Double Network & Socket Hops**: Every incoming RFC 6455 WebSocket frame is received by the proxy, decoded/buffered, forwarded over a local TCP socket, and re-decoded by the application server.
3. **Framework Event Hijacking**: Attempting to run standard Node.js proxy middlewares (e.g. Fastify with `serverFactory` or `http-proxy`) causes uncoordinated `'upgrade'` and `'request'` event listener collisions, corrupting WebSocket handshakes and throwing `ERR_HTTP_HEADERS_SENT`.

**The Objective**: Unify RouteX's high-performance edge gateway engine with Pulse's distributed messaging engine on a single Node.js `http.Server` instance listening on a single public port (e.g. `8080`), achieving zero-overhead in-memory bypass for native Pulse WebSockets and zero sidecar containers.

---

## What Makes This Cool ("Whoa" Factor)

- **Zero Sidecar Overhead**: A single Node.js process handles edge token-bucket rate limiting, circuit breakers, and upstream proxy routing alongside 10,000+ native concurrent Pulse WebSocket connections.
- **Sub-0.5ms Zero-Cost Bypass**: Native Pulse WebSocket connections bypass external network hops entirely; RouteX inspects the route and upgrade header, validates edge tokens, and immediately yields the raw Duplex socket to Pulse's `WebSocketServer.handleUpgrade`.
- **Bulletproof Fall-Through**: If an HTTP request or WebSocket upgrade does not match any RouteX edge rule, it cleanly falls through to Pulse native handlers (`/metrics`, `/healthz`, `/livez`, room WebSockets) without race conditions or header double-writes.
- **Decoupled Graceful Teardown**: Shutting down RouteX drains upstream Undici pools and Redis rate-limit connections without killing Pulse's underlying `http.Server`.

---

## Constraints & Invariants

1. **Single-Port Invariant**: RouteX and Pulse must share a single Node.js `http.Server` listening on a single public TCP port without secondary loopback ports.
2. **Master Server Ownership**: Pulse's `HttpServer` owns the lifecycle of `http.Server` (creation, port binding, listener teardown). RouteX never invokes `httpServer.close()` in embedded mode.
3. **Explicit Delegation**: RouteX must NOT unilaterally hook `server.on('request')` or `server.on('upgrade')`. Pulse explicitly calls `gateway.handleRequest(req, res)` and `gateway.handleUpgrade(req, socket, head)`.
4. **Preserve Phase 1–8 Guarantees**: Existing distributed messaging, Redis Pub/Sub, presence tracking, idempotency, cluster metrics, and chaos proxies remain 100% intact.
5. **RouteX Standalone Parity**: The underlying RouteX package (`@ankit18193/routex-gateway`) remains 100% compatible with its standalone Fastify CLI/daemon mode.

---

## Premises

1. **Single-Port Invariant**: RouteX and Pulse must operate on a single `http.Server` on one public port without sidecar containers or duplicate loopback sockets.
2. **Explicit Non-Hijacking Dispatch**: RouteX must not unilaterally hook server listeners; Pulse explicitly delegates request/upgrade to RouteX, falling back cleanly if not matched.
3. **Decoupled Lifecycle**: RouteX teardown (Undici, Redis, proxy tunnels) must not forcibly close the host `http.Server`.

## Approaches Considered

### Approach A: Explicit Dispatcher Gateway (Selected & Recommended)
- **Summary**: Enhance `RouteXGatewayServer` with `embedded: true` and explicit dispatch methods (`matchRoute`, `handleRequest`, `handleUpgrade`). Pulse's `HttpServer` delegates incoming requests and WebSocket upgrades to RouteX first, falling back to native Pulse handlers if unmatched.
- **Effort**: Medium (M)
- **Risk**: Low
- **Pros**:
  - Absolute zero risk of event listener race conditions or double upgrade writing.
  - Clean separation of concerns: Pulse retains master ownership of `http.Server` and its port.
  - Transparent fall-through for native routes (`/metrics`, `/healthz`, `/livez`, native room websockets).
  - Fastify server closure is decoupled so `gateway.close()` does not kill Pulse's server.
- **Cons**: Requires explicit coordinator wiring in Pulse.
- **Reuses**: RouteX `ProxyRouter`, `UpstreamPoolManager`, `WebSocketProxyHandler`, `RateLimitManager`, `AuthManager`.

### Approach B: Fluent Attachment Adapter
- **Summary**: Build an adapter wrapper that wraps `httpServer` listeners behind an ergonomic `attachRouteXGateway()` one-liner.
- **Effort**: Large (L)
- **Risk**: Medium
- **Pros**: One-line setup; reusable across any Node.js server framework.
- **Cons**: Higher complexity orchestrating EventEmitter order; risk of upgrade collisions.
- **Rejection Reason**: Overly complex event monkey-patching with fragile event ordering.

### Approach C: Shared In-Process IPC / Unix Domain Socket
- **Summary**: RouteX binds the public port and proxies to Pulse over an internal Unix socket / named pipe in the same process.
- **Effort**: Medium (M)
- **Risk**: Medium-High
- **Pros**: Zero changes to RouteX core.
- **Cons**: Windows/Linux socket differences; IPC serialization overhead for every frame.
- **Rejection Reason**: Incurs serialization overhead and doesn't achieve true in-memory bypass.

## Recommended Approach: Detailed Architecture

### 1. RouteX Dispatch Interface (`RouteXGatewayServer`)

```typescript
export interface GatewayServerOptions {
  readonly logger?: boolean | undefined;
  readonly redisClient?: RedisClient | undefined;
  readonly embedded?: boolean | undefined;
}

export interface RouteMatchInfo {
  readonly matched: boolean;
  readonly routeId?: string;
  readonly isWebSocket?: boolean;
}

export class RouteXGatewayServer {
  public async ready(): Promise<void>;
  public matchRoute(urlPath: string, method: string): RouteMatchInfo;
  public async handleRequest(req: http.IncomingMessage, res: http.ServerResponse): Promise<boolean>;
  public async handleUpgrade(req: http.IncomingMessage, socket: stream.Duplex, head: Buffer): Promise<boolean>;
  public async close(): Promise<void>;
}
```

### 2. Pulse `HttpServer` Dispatch Pipeline

In `src/transport/http/HttpServer.ts`:

```typescript
// On HTTP Request:
const handledByRouteX = this.routexGateway 
  ? await this.routexGateway.handleRequest(req, res)
  : false;

if (!handledByRouteX) {
  this.handleNativeHttpRequest(req, res);
}

// On WebSocket Upgrade:
const handledByRouteX = this.routexGateway
  ? await this.routexGateway.handleUpgrade(req, socket, head)
  : false;

if (!handledByRouteX) {
  this.handleNativeWebSocketUpgrade(req, socket, head);
}
```

### 3. Graceful Teardown Decoupling

When stopping Pulse (`stopCluster()`):
1. Stop accepting new incoming requests (`routexGateway.close()` returns 503).
2. Drain RouteX active proxy tunnels with deadline timeout.
3. Close Undici connection pools and disconnect RouteX Redis clients.
4. Close native Pulse WebSocket connections and rooms.
5. Close underlying `http.Server`.

## Success Criteria

1. **Single Port Verification**: A single Node.js process listens on port 8080 and handles both RouteX proxy endpoints (e.g. `/api/*`) and Pulse native endpoints (`/metrics`, `/healthz`, `/livez`).
2. **WebSocket Fall-Through**: WebSocket connections to `/ws` connect directly to Pulse native rooms, while WebSocket connections matching configured RouteX routes (e.g. `/proxy/ws`) tunnel to upstream targets.
3. **Zero Event Collisions**: No `ERR_HTTP_HEADERS_SENT` or unhandled socket errors during concurrent HTTP requests, proxy upgrades, and native room joins.
4. **Clean Teardown**: Calling cluster stop drains RouteX tunnels and closes the server cleanly with zero leaked sockets or unresolved promises.

## What I noticed about how you think

- **Pragmatic systems instincts**: You chose the explicit dispatcher pattern over brittle monkey-patching or tricky IPC sockets because you understood the real-world danger of Node.js `ERR_HTTP_HEADERS_SENT` and uncoordinated socket upgrades.
- **Obsession with zero-overhead simplicity**: When evaluating alternatives, your focus was on eliminating container sidecars and second ports without adding performance tax to native WebSocket frames.
