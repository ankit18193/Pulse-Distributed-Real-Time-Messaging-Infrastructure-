Now we ask:

This is where Pulse starts becoming an infrastructure project rather than a demo.

We'll deal with:

restore state

   ↓

We'll also establish our strategy for:

* ordering

This phase is extremely important for interviews.

# Phase 3 — Multiple Pulse Instances 📈

Now comes the **distributed system**.

Instead of:

```text
Client
  ↓
Pulse
```

we have:

```text
             Load Balancer
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
     Pulse A   Pulse B   Pulse C
```

Different users may connect to different servers.

For example:

```text
Alice → Pulse A

Bob → Pulse B
```

Now Alice sends Bob a message.

Problem:

```text
Alice
 ↓
Pulse A
 ↓
???
 ↓
Pulse B
 ↓
Bob
```

Pulse A doesn't own Bob's connection.

**This is the problem Redis will solve.**

---

# Phase 4 — Redis Pub/Sub 🚀

Now we introduce Redis.

```text
Alice
  ↓
Pulse A
  ↓
Redis PUBLISH
  ↓
Redis Channel
  ↓
Pulse B
  ↓
Bob
```

Now Pulse instances can communicate.

Example:

```text
Pulse A
   │
   │ publish
   ▼
Redis
   │
   │ subscribe
   ├──────────────► Pulse B
   │
   └──────────────► Pulse C
```

This is the heart of the distributed architecture.

We'll design:

* Redis connection management
* publisher
* subscriber
* channel strategy
* event propagation
* cross-instance room messaging
* Redis failure handling

And then prove it with an actual test:

```text
Client A
   ↓
Pulse A
   ↓
Redis
   ↓
Pulse B
   ↓
Client B
```

If that works reliably, **we have a genuine distributed realtime system.**

# Phase 5 — Distributed Presence 👥

Now we solve:

> "Who is online?"

But in a distributed environment:

```text
Ankit → Pulse A
Rahul → Pulse B
Priya → Pulse C
```

We need a shared understanding of presence.

We'll deal with:

* online/offline
* last seen
* multiple connections
* connection ownership
* distributed presence
* cleanup
* stale state

This introduces an important distributed-systems concept:

> **Eventually consistent ephemeral state.**

And we'll be careful about what Redis should and shouldn't be responsible for.

# Phase 7 — Failure & Resilience 💥

This is one of my favorite phases.

We intentionally break things.

### Kill Pulse A

```text
              Redis
             /     \
            /       \
       Pulse A     Pulse B
          X
```

What happens?

Clients connected to A should detect the failure and reconnect.

### Kill Redis

```text
Pulse A
   X
 Redis
   X
Pulse B
```

What happens?

Does local communication continue?

Do we reject certain operations?

Do we degrade gracefully?

### Other scenarios

We'll test:

* connection drops
* server crashes
* Redis failure
* malformed events
* reconnect storms
* overload
* graceful shutdown

This gives us actual **resilience engineering**.

# Phase 8 — RouteX Integration 🌐

**Only now** do we bring RouteX into the picture.

Before this phase:

```text
Client
 ↓
Pulse
```

After this phase:

```text
Client
 ↓
RouteX
 ↓
Pulse
```

RouteX becomes the edge.

It handles things such as:

* routing
* authentication
* rate limiting
* security
* HTTP proxying
* WebSocket upgrade/proxying

Pulse remains responsible for:

* realtime connections
* rooms
* messaging
* presence
* event distribution

### If RouteX doesn't support WebSockets properly

We extend RouteX.

Conceptually:

```text
HTTP Request
     ↓
   RouteX
     ↓
   routing
     ↓
HTTP upstream
```

and:

```text
WebSocket Request
     ↓
   RouteX
     ↓
Upgrade: websocket
     ↓
   Pulse
     ↓
Long-lived connection
```

This is a **very strong connection between your two projects**.
